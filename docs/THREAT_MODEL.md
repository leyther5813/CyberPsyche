# CyberPsyche Threat Model

**Project:** A Decision-Process Laboratory for Social-Engineering Resilience
**Status:** Draft — implementation controls must be verified before a participant demo or study.

## 1. Purpose and scope

CyberPsyche is a research prototype for studying whether a short, behavior-targeted intervention improves independent verification and transfer across social-engineering scenarios. It uses simulated messages and schema-controlled ground truth.

This document identifies foreseeable risks and the controls that must be checked. Listing a control here does not mean it has already been implemented.

## 2. Assets to protect

- Participant accounts, authentication data, and consent records.
- Pseudonymous behavioral events, decisions, response times, and intervention assignments.
- Scenario definitions, hidden ground truth, diagnostic clues, and scoring rules.
- Research exports and researcher access.
- Application secrets, database credentials, audit records, and backups.

## 3. Threats and required controls

| Threat | Required control | Verification |
|---|---|---|
| Password disclosure or account takeover | Use Argon2id or bcrypt; secure authentication; rate-limit login attempts | Inspect configuration and test authentication |
| Unauthorized record access | Enforce ownership checks and researcher role checks server-side on every applicable endpoint | Test access using different users and roles |
| Ground truth exposed before a decision | Keep truth and scoring server-side; return only information permitted in the current session phase | Inspect API responses and test all phases |
| Forged or out-of-order decisions | Validate session ownership, phase, scenario assignment, and state transitions server-side | Add negative integration tests |
| SQL injection | Use ORM parameterization and validated inputs | Review queries and run security checks |
| Cross-site scripting | Escape or sanitize untrusted content; apply a restrictive Content Security Policy | Inspect rendering and response headers |
| CSRF or stolen session | If cookie-based sessions are used, configure SameSite appropriately and implement CSRF protection; protect tokens | Verify the actual session design |
| Brute force or resource exhaustion | Apply rate limits, request-size limits, safe timeouts, and bounded input validation | Test limits and oversized requests |
| Sensitive information in free text or logs | Warn participants not to enter private information; minimize collection; redact sensitive values from logs | Inspect forms, logging, and stored records |
| Re-identification through exports | Export only necessary pseudonymous fields; exclude direct identifiers and free text unless specifically approved | Inspect exported CSV files |
| Accidental data loss | Maintain restricted backups and document restoration procedures | Perform a controlled restore test |
| Secret leakage or vulnerable dependencies | Keep secrets in environment configuration; audit dependencies and repository contents | Run dependency and secret scans |
| Unsafe simulated content | Use fictional brands, domains, identities, and contact details; never include functional malicious links or request real credentials or OTPs | Review the complete scenario library |

## 4. Trust boundaries

- The browser is untrusted; the backend must enforce authorization, validation, phase transitions, and scoring.
- The database stores research records and scenario truth; access must be restricted.
- Research exports are a separate disclosure boundary and require authorization and pseudonymization.
- Scenario text is data, not executable instructions. Do not allow scenario content to alter scoring or application behavior.

## 5. Research integrity controls

- Ground truth must be schema-controlled, not generated by an LLM at runtime.
- Scoring must be rule-based and reproducible.
- Do not reveal per-item truth or corrective feedback before the protocol permits it.
- Keep baseline, intervention, retest, and transfer assignments consistent with the approved protocol.
- Preserve an auditable record of relevant state changes without unnecessarily storing sensitive information.

## 6. Release checklist

Before a participant-facing demo or study, verify and record:

- [ ] Authentication and password storage.
- [ ] Authorization and participant ownership checks for every endpoint.
- [ ] Server-side scoring and no early ground-truth disclosure.
- [ ] Input validation, rate limiting, request-size limits, and safe errors.
- [ ] Security headers, including CSP, HSTS in HTTPS deployment, and X-Content-Type-Options.
- [ ] CSRF protections if cookie-based authentication is used.
- [ ] Pseudonymized research exports and restricted researcher access.
- [ ] Dependency/security scan, such as Semgrep or OWASP ZAP where appropriate.
- [ ] Backup and restoration test.
- [ ] Scenario safety review and privacy/deletion workflow.
- [ ] Review against the project's threat model and applicable OWASP ASVS checklist.

**Release decision:** Do not mark a control complete until it has been checked against the running implementation and the evidence has been recorded.
